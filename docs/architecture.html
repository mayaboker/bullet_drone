Domain boundaries

Four distinct software domains, each with its own clock, state, and data ownership.

Physical Simulation
bullet_drone/ · Process 1
  • PyBullet or PhysX backend (swappable)
  • Rigid-body dynamics at 240 Hz
  • Motor → propeller → force chain
  • Sensors: IMU, barometer (modelled)
  • Flight controller (attitude + rate PID)
  • Accepts 18-ch RC, outputs DroneState
Rendering Engine
bullet_render/ · Process 2
  • Isaac Sim with RTX renderer
  • USD world (terrain, lighting, truck)
  • Front camera render product
  • Frames shared via POSIX shm
  • Viewport UI + pick-to-place controls
  • Receives drone pose, outputs camera pixels
Mission
bullet_app/ · Process 3 (upper half)
  • HSV colour detection (no ML)
  • State machine: TAKEOFF → HOVER → YAW_SEARCH → YAW_CENTER → YAW_SETTLE
  • Decides when to search, track, or abort
  • Owns lifecycle commands (start/stop/reset)
  • Hands off bearing to LOS once centred
LOS Tracking
los_tracking/ · Process 3 (lower half, library)
  • BearingEstimator (α-β on bbox)
  • TtcEstimator (1/size regression)
  • VerticalEstimator (α-β on baro)
  • LosControl (PID → roll, pitch, vz)
  • Stages: BEARING → TTC → TERMINAL
  • Outputs RC channels to physics
  • Recovery on target loss or over-tilt
  • Descent feasibility gate
  • Anti-windup, slew limiting, tilt cap

Key distinction: Mission decides what to do (search, centre, hand off, abort). LOS Tracking decides how to fly toward the target (bearing estimation, proportional navigation, control law). Physical Simulation turns RC commands into forces (flight controller, motor mix, rigid-body dynamics). Rendering Engine turns drone state into pixels (USD scene, RTX camera, shared-memory frames).

Process 3 threading (bullet_app with --mission-config)

Three threads, three rates. Vision feeds control, control feeds physics. Main thread is display only.

Vision thread ~500 Hz runtime.py:54 · _vision()
receiver.poll() → detect_red_box() → latest_vision = (meta, bbox) → wait(0.002) if idle
Polls ZMQ non-blocking. Runs HSV detection on every new frame. Writes result under lock.
↓ self.latest_vision under threading.Lock ↓
Control thread 100 Hz fixed runtime.py:71 · _control() · COMMAND_PERIOD_S = 0.01
recv feedback :5555 → read latest_vision → mission.tick() → send RC :5559 → wait(remaining)
Fixed 100 Hz timer. Runs Mission FSM + LOS navigator each tick. Publishes RC channels to physics. This is the heartbeat.
↓ self.status + self.display under same lock ↓
Main thread ~20 Hz runtime.py:194 · run_mission()
read status → print() / cv2.imshow() → wait(0.05)
Display only — no detection, no control. Console output at ~20 Hz, or OpenCV window at ~100 fps with --debug.
Why separate? Vision is decoupled so the control loop never waits for a frame — it reads the latest available bbox each tick. The control thread runs at a fixed 100 Hz matching COMMAND_HZ in physics, because the PID controllers and α-β estimators need a steady dt. The main thread stays slow because it only serves the human watching the terminal.
